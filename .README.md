# Local LLM Proxy Gateway

An asynchronous FastAPI proxy gateway that intelligently routes user prompts to isolated, locally hosted Large Language Models (LLMs) running inside Docker containers. 

## 1. System Architecture
This project utilizes a microservices architecture to ensure isolation and scalability:
* **Gateway (FastAPI):** Acts as the entry point, receiving POST requests and routing them to the appropriate model based on the URL path. It handles asynchronous connections and error management.
* **Worker 1 (Phi-3):** A dedicated container running the official Ollama image, serving the Microsoft `phi3` model for tasks requiring complex reasoning and logic.
* **Worker 2 (TinyLlama):** A dedicated container serving the `tinyllama` model for high-speed, low-latency text generation.
* **Storage:** Persistent Docker Volumes are used to store the multi-gigabyte model weights locally, ensuring containers remain stateless while avoiding repeated downloads on startup.

## 2. Setup Instructions and How to Run

**Prerequisites:** * Docker Desktop must be installed and running.
* At least 5-10 GB of free local storage for the LLM weights.

**Step 1: Clone the repository**
```bash
git clone [https://github.com/Youssof10/LLM-Proxy-Service.git](https://github.com/Youssof10/LLM-Proxy-Service.git)
cd LLM-Proxy-Service
```

**Step 2: Build and start the architecture**
```bash
docker-compose up -d --build
```

**Step 3: Download the Model Weights**
Model weights are intentionally excluded from the repository. Pull them directly into the persistent volumes by running:
```bash
docker exec -it model-tinyllama-container ollama pull tinyllama
docker exec -it model-phi3-container ollama pull phi3
```
*(Wait for both downloads to say "success" before proceeding).*

**Step 4: Test the API**
Send a POST request to the proxy gateway on port 8000.

Test the Fast Model (TinyLlama):
```bash
curl -X POST http://localhost:8000/generate/tinyllama \
-H "Content-Type: application/json" \
-d '{"prompt": "Say hello to a Data Scientist!"}'
```

Test the Smart Model (Phi-3):
```bash
curl -X POST http://localhost:8000/generate/phi3 \
-H "Content-Type: application/json" \
-d '{"prompt": "What are the three main pillars of Data Science?"}'
```

## 3. Assumptions
* **Compute Constraints:** The architecture assumes execution on standard CPU hardware rather than dedicated GPUs.
* **Port Availability:** It assumes port `8000` (FastAPI) and internal container ports `11434` (Ollama) are available.
* **Network Independence:** Assumes the user wants a completely private, offline inference environment once the initial weights are downloaded.

## 4. Challenges
* **Hardware Constraints & Framework Limitations:** Initially, the project was built using the `transformers` and `torch` libraries to run lightweight models like `gpt-2` and `distilgpt2`, as the target hardware lacks a dedicated GPU. However, the qualitative accuracy and contextual understanding of these older models were too low for a practical application. 
  * *Solution:* Pivoted the architecture entirely to use **Ollama**. Ollama is highly optimized for CPU inference (utilizing `llama.cpp` under the hood), which allowed the system to run much more capable, modern models (like Phi-3) locally without requiring a GPU.
* **CPU Inference Timeouts:** Running a 3.8-billion parameter model (Phi-3) on a CPU caused the FastAPI gateway to drop the connection before the model finished generating text. 
  * *Solution:* Implemented a custom 300-second timeout in the `httpx.AsyncClient` to accommodate hardware-bound latency constraints.
* **Container Race Conditions:** Attempting to auto-pull the models via the Docker `entrypoint` script caused race conditions where the API would receive requests before the multi-gigabyte download completed, resulting in "model not found" errors. 
  * *Solution:* Decoupled the weight-fetching process from the container startup and relied on manual initialization combined with persistent volumes.

## 5. Design Decisions
* **Iterative Framework Pivot:** Transitioning from Hugging Face `transformers` to `Ollama` was a deliberate decision to maximize the quality of the LLM output while strictly adhering to the CPU-only hardware limitation.
* **FastAPI for the Gateway:** Chosen for its native asynchronous capabilities (`async`/`await`), which is critical when acting as a proxy for slow, I/O-bound LLM generation tasks.
* **Model Selection:** `Phi-3` was selected to demonstrate capability with dense, highly capable reasoning models, while `TinyLlama` was included to demonstrate a lightweight, high-throughput alternative. 
* **Docker Volumes over Bind Mounts:** Used named Docker Volumes (`phi3_data`, `tinyllama_data`) instead of local folder binds to keep the heavy weights safely managed within the Docker ecosystem and prevent accidental Git commits of massive files.
* **Transparent Error Handling:** The proxy is designed to cleanly catch native Ollama engine errors (like missing weights) and pass them through the gateway rather than swallowing them, ensuring better API observability.
